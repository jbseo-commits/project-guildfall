# CORE LOOP — WORKING MODEL

This is a hypothesis, not a locked implementation.

## Macro

Acquire / alter build → choose next challenge → prepare → autobattle → debrief → adapt → repeat.

## Micro battle loop

### 1. Threat read
The player receives enough information to make a meaningful plan, but not perfect information.

### 2. Build action
The player makes one or more choices that materially change battle behavior.

### 3. Commit
A clear button/gesture locks the plan.

### 4. Automatic resolution
The fight runs with minimal or no direct micro-control.

Recommended first prototype length: **5–15 seconds**, not a 60-second spectator match.

### 5. Causal debrief
Show 1–3 decisive events, not an analytics wall.

Examples of useful feedback:
- “Your frontliner held the assassin for 2.1s, letting the ritual complete.”
- “Both healers targeted the same ally; 38% of healing was wasted.”
- “The fire chain triggered three times because the marked enemy stayed grouped.”

### 6. Adapt
Give one interesting decision quickly enough that the player mentally connects it to the previous battle.

## Success test

After one failed fight, the player should be able to say:

> “I know one thing I want to change.”

After one successful fight:

> “That thing I built actually happened on screen.”
